# Модель данных привязки «дух ↔ игрок»

*Исполняющая часть Конституции. Реализует Статьи III (петля), IV (сон-зеркало) и V (присутствия).*
*Платформа: NeoForge (основной путь) + заметка по legacy Forge.*

## Несущий принцип реализации

> **Привязка (Bond) — это запись и единственный источник истины. Присутствие (моб) — её одноразовая проекция.**

Запись переживает выгрузку чанка, смерть игрока и перезапуск мира. Моб — нет: он спавнится по нужде, читает и пишет в запись, а при деспавне умирает, не унося состояние. Это и есть выбранная архитектура: убивать моба дёшево, терять привязку — нельзя.

Из одного принципа следует всё остальное: сон — это `render(состояние игрока)`, живой мир — это `состояние чанков`, ритуал и амулет — это операции `создать/изменить/запечатать` над записями. Четыре механики оказываются **запросами к одному состоянию**, а не четырьмя подсистемами.

---

## Карта: три якоря и одна запись

Запись о привязке (`Bond`) крепится к одному из трёх **якорей**, в зависимости от того, *кто держит привязку*:

| Якорь | Что хранит | Механизм NeoForge |
|---|---|---|
| **Игрок** (`PlayerSoulData`) | метки на ведьме, носимые амулеты (ссылки), суммарный долг/вес внимания | `AttachmentType` на `Player` |
| **Место** (`ChunkSoulData`) | собственные привязки мира, «потревоженность» чанка | `AttachmentType` на `LevelChunk` |
| **Предмет** (`SealedBond`) | запечатанная в амулет привязка | `DataComponentType` на `ItemStack` |

**Присутствие** (`PresenceEntity`) ни к чему не «принадлежит» — оно держит только `bondId` и обращается к записи по нему. Это проекция, а не якорь.

---

## 1. Дух (`SpiritType`) — шаблон, не экземпляр

Статические, data-driven данные (реестр / датапак). Описывает *вид* присутствия, а не конкретную привязку.

```
SpiritType {
  id: ResourceLocation         // wmod:forest_warden
  domain: Correspondence        // лес / камень / вода / порог ... (словарь Закона)
  baseDisposition: Disposition  // врождённый настрой вида
  projection: EntityType        // в какого моба проецируется
  wants: List<Demand>           // чего требует для умилостивления (привязка к ритуалу)
  dialoguePool: DialogueRef     // НЕ случайные фразы — реплики, индексированные по состоянию
}
```

Один `SpiritType` порождает тысячи `Bond` — как один класс порождает экземпляры.

---

## 2. Привязка (`Bond`) — источник истины

Сериализуемая запись (Java `record` + `Codec`). Ядро всей системы. Поля прямо отражают то, что мы назвали: происхождение, долг, метки, история.

```
Bond {
  bondId: UUID                  // стабильная идентичность
  spiritType: ResourceLocation  // какой шаблон духа

  // ── ПРОИСХОЖДЕНИЕ (откуда высвобожден) ──
  origin: {
    pos: BlockPos               // где
    dimension: ResourceKey
    cause: ReleaseCause         // FELLED_TREE / BROKE_ANCIENT_STONE / RITUAL_SUMMON ...
    sourceBlock: Block
    bornTick: long              // когда
  }

  // ── ДИСПОЗИЦИЯ (числовые мотиваторы — Статья V) ──
  disposition: {
    debt: float        // СКОЛЬКО ИГРОК ДОЛЖЕН этому духу (растёт, пока тянет силу)
    resentment: float  // обида (растёт от потревоженности и неоплаченного долга)
    fear: float        // страх
    loyalty: float     // верность (растёт от умилостивления/кормления)
  }

  // ── МЕТКИ (что эта привязка налагает на держателя) ──
  marks: List<Mark>             // Mark { scope: BIOME/DOMAIN/GLOBAL, severity }
                                // «лес помнит, ты помечена» = Mark{BIOME:forest}

  // ── ПЕЧАТЬ (различает ритуал и амулет) ──
  seal: SealRef | null          // null = свободна/активна (ритуальная, транзиентная)
                                // не-null = запечатана в предмет (амулет, постоянная)

  // ── ИСТОРИЯ (память духа) ──
  ledger: List<LedgerEntry>     // append-only: RELEASED, APPEASED, BETRAYED, FED, SPOKE...
                                // из неё считается дрейф диспозиции И контекст диалога

  lastResolvedTick: long
}
```

`seal == null` → привязка живёт в чанке/у игрока как активная метка (результат ритуала).
`seal != null` → привязка запечатана в амулете (постоянный эффект ценой долга).
**Это один и тот же тип записи** — ритуал и амулет различаются только полем `seal` и сроком жизни. Ровно тот синтез, к которому мы шли: не три механики, а одна запись в трёх состояниях.

## 3. Якоря хранения

**`PlayerSoulData`** — `AttachmentType` на `Player`:
```
PlayerSoulData {
  marks: List<Bond>          // привязки, что МИР наложил на ведьму (свободные)
  amulets: List<UUID>        // ссылки на запечатанные Bond в надетых амулетах
  totalDebt: float           // Σ debt по носимым → «вес внимания мира»
  essence: float             // общий ресурс (петля)
}
```
Это то, что читает генератор снов. **Должна переживать смерть** — смерть не оплачивает долг (копирование при респавне).

**`ChunkSoulData`** — `AttachmentType` на `LevelChunk`:
```
ChunkSoulData {
  disturbance: float            // насколько потревожено место (дефолт-гранулярность: чанк)
  rootedBonds: List<Bond>       // собственные привязки мира, рождённые здесь
}
```
Сериализуется вместе с чанком — память места хранится бесплатно и локально.

**`SealedBond`** — `DataComponentType` на `ItemStack` (амулет):
```
SealedBond { bond: Bond }      // вся запись живёт в самом предмете
```
В современном MC данные предмета — это компоненты, не NBT. Амулет *носит свою привязку с собой*; надевая его, игрок добавляет `bondId` в `PlayerSoulData.amulets`.

---

## 4. Присутствие (`PresenceEntity`) — моб по нужде

Моб держит **только** `bondId`. Всё его состояние — в записи.

**Когда спавнится (проекция, не сущность):**
- игрок входит в радиус потревоженного чанка (`disturbance` высока) → мир рождает присутствие;
- в **сне** — генератор читает `PlayerSoulData` и спавнит проекции носимых/помеченных привязок;
- `disposition` пересекает порог (например `resentment` высок) → дух является, чтобы предъявить счёт.

**На деспавне/выгрузке** — моб умирает, `Bond` остаётся нетронутым. Источник истины не зависит от того, загружен ли моб.

---

## 5. Динамика диспозиции — вычисляется, не бросается костью (Статья II.6)

Дрейф мотиваторов — функция от `ledger` и времени, событийно:

```
пока seal != null (амулет тянет):   debt += drawRate * dt
если debt не гасится:               resentment += f(debt) * dt
APPEASED (ритуал умилостивления):    resentment -= k ;  loyalty += k
BETRAYED (сломал связанное):         resentment += большой скачок
FED / дар:                           loyalty += ...
рост disturbance в месте:            resentment всех rootedBonds += ...
```
Никакого `random` там, где игрок должен мочь предсказать. Случайность допустима только как *объявленная* цена непредсказуемости духов, не как замена логики.

---

## 6. Поведение и речь как функция состояния (Статья V)

**Поведение** — utility-AI: оценка каждого действия = функция от вектора `disposition`. Враждебность, бегство, помощь, преследование — всё ранжируется из чисел. Групповое поведение — дёшево: `disturbance` чанка задаёт мотиваторы всем `rootedBonds` разом.

**Реплика** — выбирается по ключу `(spiritType, доминирующий мотиватор, контекст из ledger)`, а не из общего пула. Дух «помнит», что с ним сделали, потому что фраза — проекция записи.

**Инициация разговора** — когда истинен предикат «счёта»:
```
hasGrievance(bond) = debt > T1 || resentment > T2 || есть непогашенная Mark
```
Разговор начинается по счёту, не по таймеру.

*Детерминированное ядро. Языковая модель — опциональный слой поверх (Статья V.5), никогда фундамент: она может переформулировать реплику, выбранную ядром, но не выбирать её.*

---

## 7. Четыре механики = запросы к одному состоянию

Вот ради чего всё строилось — синтез на уровне операций над `Bond`:

- **Ритуал** → `создать` свободную привязку (высвобождение из мира) **или** `изменить` существующую (умилостивить: `−resentment +loyalty`; связать: выставить `seal`). Один раз пишет в `ledger`.
- **Амулет** → `запечатать`: выставить `seal`, перенести `Bond` в `SealedBond` предмета. Носка → постоянный эффект ценой растущего `debt` в `PlayerSoulData`.
- **Живой мир** → при разрушении помеченного блока бросок против «плотности духа» → `создать` rooted-привязку в `ChunkSoulData`, поднять `disturbance`, по желанию сразу спроецировать `PresenceEntity`.
- **Сон** → `render(PlayerSoulData)`: читает носимые привязки и их `ledger`, населяет сон проекциями. Внутри сна можно `изменить/разорвать` записи (договор, разрыв связи) — и это разрешается наяву.

Четыре глагола — `создать / изменить / запечатать / читать` — над одной таблицей. Это и есть «язык», а не «набор слов».

---

## 8. Петля в терминах данных (Статья III)

```
разрушил древний блок
  → ChunkSoulData.disturbance↑ ,  new rooted Bond ,  essence↑   (высвобождение)
essence → ритуал/амулет создаёт/печатает Bond                    (привязка)
носимый Bond → PlayerSoulData.totalDebt↑                         (долг)
totalDebt↑ → дисп. ближних Bond растёт, spawn-вес растёт          (мир враждебнее)
  → чтобы погасить, нужен новый ритуал → нужна новая добыча → ⟳
```
Источник силы (`essence` из разрушения) и источник опасности (`disturbance` + `debt`) — буквально одни и те же поля. Петлю нельзя разорвать, не выкинув поле.

## 9. Сквозной пример

###
example
**Амулет из сердцевины древнего дерева — путь через структуры данных:**

1. Игрок валит древнее дерево. `cause = FELLED_TREE`, бросок проходит → в `ChunkSoulData` рождается `Bond{ spiritType: forest_warden, disposition: {resentment: 0.6} }`, `disturbance += 0.4`, `essence += N`. Сразу спавнится `PresenceEntity(bondId)` — потревоженный страж.
2. Игрок тратит `essence` в ритуале → операция `запечатать`: у `Bond` выставляется `seal`, запись переносится в `SealedBond` амулета. Добавляется `Mark{ scope: BIOME:forest, severity: 0.5 }`.
3. Надевает амулет → `bondId` в `PlayerSoulData.amulets`. Эффект (сродство с лесом) активен. Но `debt += drawRate` каждый тик, и `Mark` помечает её: лесные присутствия в любом лесу видят `hasGrievance == true` и враждебны.
4. Долг растёт, `resentment` ползёт вверх. Однажды во сне генератор читает `PlayerSoulData`, видит этот `Bond` с высоким `resentment` → спавнит проекцию стража прямо в сон. Срабатывает предикат счёта → страж заговаривает.
5. Во сне игрок либо `изменяет` запись (договор: гасит `debt`, `loyalty↑`), либо `разрывает` `seal` (амулет рассыпается наяву, но `Mark` снимается). Запись — источник истины — меняется, и наяву всё разрешается соответственно.

Один объект завязал ритуал, амулет, живой мир и сон в узел — потому что все четыре читали и писали одну запись.

## 10. Заметки по персистентности (Forge / NeoForge)

- **NeoForge (осн. путь):** `PlayerSoulData` и `ChunkSoulData` — `AttachmentType`, зарегистрированные через `DeferredRegister<AttachmentType<?>>`, сериализация через `Codec`. `SealedBond` — `DataComponentType` на стэке. Чанковый аттачмент сохраняется с чанком автоматически; игроцкий — пометить копированием при смерти/респавне (долг переживает смерть).
- **Сам `Bond`** — `record` + `Codec` через `RecordCodecBuilder`, переиспользуется во всех трёх якорях.
- **Legacy Forge (1.20.1):** то же, но `AttachmentType` → Capability (`RegisterCapabilitiesEvent`, `AttachCapabilitiesEvent` для игрока/чанка, `INBTSerializable<CompoundTag>` для сейва), а `DataComponentType` амулета → NBT на стэке.
- *API аттачментов на NeoForge эволюционировал между версиями — точные сигнатуры билдеров сверь со своей версией. Здесь зафиксирована форма данных, а не имена методов.*

## Что я закрыл дефолтами (переопределяемо)

Как и договаривались — эти решения принял за разумные значения, меняй под себя:

1. **Гранулярность памяти мира — чанк** (`disturbance` на `LevelChunk`). Дёшево, скейлится, переживает выгрузку. Альтернатива: регион (грубее, дешевле) или помеченные блоки точечно (дороже, точнее) — для плотных узлов можно совместить.
2. **Скоуп меток — домен/биом** (`Mark.scope`). Можно сузить до конкретных координат или расширить до глобальной.
3. **Долг — функция времени и тяги** (`debt += drawRate`). Можно сделать ступенчатым (за событие), а не непрерывным.
4. **Канонический реестр привязок** — пока хранится прямо на якоре. Если cross-anchor поиск по `bondId` станет тяжёлым, вынеси в `SavedData`-реестр уровня, а якоря оставь со ссылками.
